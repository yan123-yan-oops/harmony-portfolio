# 架构与设计说明

三个应用共享同一套分层思路：**页面只做展示，状态与业务在 ViewModel/Service，数据在 Model/DAO。**

## 分层

```
┌─────────────────────────────────────────────┐
│ pages / components      只负责 UI 与事件绑定  │
├─────────────────────────────────────────────┤
│ viewmodel               状态编排、调用服务    │
├─────────────────────────────────────────────┤
│ services                网络 / 云函数 / 音频  │
├─────────────────────────────────────────────┤
│ model                   类型定义与字段映射    │
├─────────────────────────────────────────────┤
│ database (RDB)          SQL 与 ValuesBucket  │
└─────────────────────────────────────────────┘
```

**规则**：
- 页面不写 SQL、不拼请求体；
- Service 不碰 UI 状态；
- Model 的字段映射只有一个入口（如 `mapApiResponse`）。

## 网络层四层封装

```
业务调用  api.getQuestions(page)
          │
业务层    services/question.ts        ← 只写参数与返回类型
          │
拦截层    token 注入 / 剥壳 / 401 跳登录 / 统一错误
          │
请求层    axios 实例（可与 AI 请求隔离）
```

为什么这样分：新增接口只写一个业务函数；鉴权与错误处理只改一处。

## 状态管理

| 场景 | 方案 | 说明 |
| --- | --- | --- |
| 页面内 | `@State` | 组件自己持有 |
| 父子 | `@Link` / `@Prop` | 单向或双向绑定 |
| 跨页面 | `AppStorage` | 登录态、用户信息 |
| 全局事件 | `Emitter` | 播放状态广播，避免层层传 props |

## 性能

| 问题 | 手段 |
| --- | --- |
| 长列表卡顿 | `List` + `LazyForEach`，只渲染可视区域 |
| 启动慢 | 延迟初始化非首屏资源；状态对象保持轻量 |
| 播放器资源泄漏 | 单例统一管理生命周期，页面退出时释放 |

## 鸿蒙特有的注意点

1. **ArkTS 不是 TypeScript**：禁 `any`、禁动态 `import()`、禁索引签名、对象字面量必须标注类型；
2. **`catch` 不能标类型**，要 `as BusinessError` 后再包装；
3. **路由要登记**：只有 `router.pushUrl` 跳转的页面才需要写进 `main_pages.json`，Tab 子页不需要；
4. **`oh_modules`/`build` 不进仓库**，但 `oh-package.json5` 与 `build-profile.json5` 要进。
